# 07: 求解失败与数值兜底（M5）

Status: ready-for-agent
Type: task

**What to build:** 让节点在最坏情况下**活着**，并且**不发错指令**。

两条都是摔机级的：节点一崩，offboard 心跳停发 → PX4 触发失效保护；而发一条"语法完全合法、方向却是错的"指令，**PX4 会照做**。

**Blocked by:** [06](06-mpc-node-fake-px4-fixture.md)

- [ ] 求解失败**绝不 `raise`** —— 保持上一帧可行指令，或切到安全悬停（悬停推力 + 零角速率）
- [ ] 发布前 `np.isfinite()` **全量校验**：任一项非有限则**整帧丢弃**并走上面的兜底
      ★ 第一手依据：PX4 对角速率的三个分量有 NaN 回退（退回实测角速率），**推力没有** —— 一个 NaN 推力会直达混控器
- [ ] **连续**求解失败达阈值 → 置标志并上报，使这个事件在飞行日志里是**可检索**的
- [ ] 收到**不符合预期的状态**（时间戳倒退、位姿跳变）时选择**不发指令**，而不是发错指令
- [ ] 全部走 [06](06-mpc-node-fake-px4-fixture.md) 夹具的**故障注入**用例覆盖：求解失败 / 非有限值 / 时间戳倒退 / 位姿跳变 —— 这是夹具必须能注入故障的理由
- [ ] 保证 SITL 里的注入手段可用（判据 4 由 [11](11-sitl-tier-b-seam3.md) 跑）
- [ ] M5 的改动编号与依据已记入 [`phase2-implementation.md`](../../../docs/control/phase2-implementation.md)

---

**为什么单独成张而不是并进 06**：它的失败模式与"节点正常工作时发什么"完全不同 —— 前者是**时序与异常路径**，后者是**数值与映射**。而且它需要夹具具备故障注入能力之后才有意义，所以天然排在 06 之后。这两张合起来会超出一个上下文窗口。
