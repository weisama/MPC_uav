# 04: `mocap` 节点 —— 相对位姿 + 两阶段原点 + 仅归零 yaw

Status: ready-for-agent
Type: task

**What to build:** 动捕位姿变成「以我摆放飞机的位置为原点的相对位姿」并喂给 EKF2，使 **QGC 在解锁之前就已经有稳定收敛的位置估计**。

这是 Phase 1 第一次让飞控"看见"动捕，也是**全栈唯一一个做坐标处理的节点**。

**三个已定的决策（本 ticket 只是实现它们，不要重新推导）：**

1. **只做「减原点 + 归零 yaw」，不做任何坐标系转换。** 输出**动捕原生 ENU/FLU**，ENU→NED 与 FLU→FRD **全由 mavros 在自己的边界上完成**（已读 mavros 源码确认，见 [`phase1-implementation.md`](../../../docs/control/phase1-implementation.md) §3.5）。所以本节点**不发 NED 话题** —— 那个话题没有任何消费者，删掉它同时消灭了"转两次 / 一次都没转"这一整类 bug。
2. **原点分两阶段。** 节点启动先用"启动原点"持续发 vision_pose（保证**解锁前 EKF2 不断粮、已收敛** —— 等到解锁那一刻才第一次喂，EKF2 能否干净初始化是未验证的）；**解锁上升沿**切到"起飞前静止帧"原点。切换**不得产生位置跳变**，前提是**启动到解锁之间不要搬动飞机**（★ 不是"必须朝某个方向摆放"，而是"摆好后到解锁前别动它"）。
3. **姿态只归零 yaw，roll/pitch 保持绝对。** 整个姿态做相对会让"水平"的定义变成"解锁时那个姿态" —— 地面不平、起落架软，解锁时有几度横滚就会让飞机持续单向漂移，而 EKF2 认为误差是零，控制器看不出来。

**为什么这张要单独做（也就是为什么它值一张 ticket）：** 位姿处理错误**在话题层面没有诊断分辨率** —— 飞机往反方向飞时，话题上分不出是原点锁错、yaw 归零错、还是 mavros 的边界转换不如预期。所以这里含**全项目唯一的纯函数单测**（seam 2），成本≈0，挡住的是"飞起来才发现"的一整类错误。

**Blocked by:** 03

- [ ] **未解锁时** QGC 的 `LOCAL_POSITION_NED` **已稳定**，且有 `VISION_POSITION_ESTIMATE`（台架上可验，不用飞、不用解锁）
- [ ] 解锁上升沿切原点，**切换瞬间位置无跳变**；原点锁定时刻记入日志
- [ ] 位置输出**逐轴独立** —— 不受姿态处理影响
- [ ] 姿态归零后**机体 z 轴方向不变**；roll/pitch 未被归零
- [ ] **时间戳原样转发** `vrpn_listener` 的 stamp，**不二次打戳**（mavros 会静默丢弃时间戳不前进的消息）
- [ ] **坐标系确认实验**：把飞机向动捕 **+x 方向（东）平移 0.5 m** → QGC 的 **`y` 变化 0.5**；再**升高 0.3 m** → QGC 显示**向上**
- [ ] 三个纯函数（原点减法 / 仅归零 yaw / 两阶段原点切换）各自有单测，**零 ROS 依赖**
- [ ] `/mocap/pose_enu` 发布（Phase 1 只用于记录；Phase 2 拿它当状态源）

---

**关于"只归零 yaw"的一个连带结论**（记在这里以免后人重新论证）：因为 EKF2 融合视觉 yaw 后会把世界系对齐到动捕坐标系，所以 PX4 的"北"就是动捕的 +x，**机头朝哪都行**。旧文档里"机头必须朝假定东"的仪式不再必要 —— 但「启动到解锁之间保持静止」这条纪律**仍然必要**。
