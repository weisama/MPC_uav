## Problem Statement

我有一台组装完成、只用遥控器飞过的四旋翼 **z0**（OddityRC XI35 Pro，152 mm 涵道机，微空 NxtPX4v2 飞控，Jetson Orin NX 机载，Nokov 动捕定位）。最终目标是让 **MPC（模型预测控制）** 接管飞控内置 PID。

> ⚠️ **固件版本（2026-09-20 更正）**：本项目文档旧称 z0 跑 "PX4 1.14.x"，**这个标签是错的**。飞控固件真身 = `Peize-Liu/PX4-Autopilot` @ `5ba2e91f`，**属 v1.15 世代**（第一手判定，见 [`refs-manifest.md`](../../docs/reference/refs-manifest.md) §2.5）。**实际烧录版本以 QGC 读出的为准**，那是唯一终审。这条更正直接影响 `px4_msgs` 选版（Phase 2）。

问题是：**z0 目前没有任何自主飞行能力。** 我的动捕定点飞行经验全部来自另一台机器（超维空间 S2-F290 + Pixhawk + PX4 1.13.3），换了机架、换了飞控、换了机载电脑，这条链路必须重做一遍——EKF2 参数、外参标定、串口、固件行为全都不同。

如果我先建 MPC（模型预测控制）再上机，一旦飞机表现不对，我**无法二分定位**故障在哪：是 MPC 的模型/代价/约束写错了，还是动捕→offboard 这条基础链路本身就不通？这两类问题在现象上高度相似（飘、抖、不跟点），而排查路径完全不同。同时引入两个新变量，是我在这台机器上最不能承受的风险。

**从我的角度，我要的是**：先把"动捕 → 机载电脑 → offboard → 飞控 → 飞机"这一条链单独跑通并稳定，让它成为一个**已被验证的、可复用的底座**；之后 MPC 只是往这个底座上追加一层，而不是从头搭。

## Solution

实现 **Phase 1：offboard (A) 级位置控制**。机载电脑把动捕位姿转成目标位置与偏航，通过 **mavros2** 的 `/mavros/setpoint_raw/local` 下发给飞控；**PX4 承担全部内环**（位置环、姿态环、角速率环、混控）。

具体交付：

1. **动捕链路**：复用已验证的 `vrpn_listener`（vendored 原样），在其上重写一层相对位姿处理——以未起飞时的静止帧为原点，输出相对位置；姿态只归零偏航。
2. **飞行状态机**：显式区分「谁在控制飞机」与「程序在干什么」，覆盖解锁、起飞、悬停、轨迹跟踪、降落，以及各类超时与失效保护。
3. **三条参考轨迹**：启动脚本后输入数字选择——①起飞 1 m 原地悬停，②悬停稳定后划边长 1 m 的正方形，③悬停稳定后划半径 0.5 m 的 8 字。
4. **安全机制**：遥控器夺权、offboard 心跳丢失失效保护、消息超时、指令限幅。

**Phase 1 全程不引入** MPC（模型预测控制）、acados、uXRCE-DDS——见 Out of Scope。

## User Stories

### 动捕链路

1. 作为操作者，我想让 z0 用的动捕数据来自**已经实机验证过的** `vrpn_listener`，这样我不必重新验证一个已经能工作的组件。
2. 作为开发者，我想让 `vrpn_listener` 以 vendored 形式原样进仓库并标注「勿替换」，这样未来的我不会误把它换成上游公开版本而破坏已验证的行为。
3. 作为开发者，我想让动捕节点的**时间戳原样转发**上游的 stamp 而非二次打戳，这样 EKF2 不会认为数据比实际更新。
4. 作为操作者，我想让飞机**未起飞时的静止位置**被自动记录为坐标原点，这样我不需要每次飞行前手动测量和填写原点坐标。
5. 作为操作者，我想让动捕输出的位置是**相对原点的偏移**而非动捕棚的绝对坐标，这样我换一个场地飞行时不需要改任何配置。
6. 作为操作者，我想让动捕无人机体的**偏航被归零**，这样飞机的"机头方向"以我摆放它的方向为准，而不必对齐动捕棚的某个坐标轴。
7. 作为操作者，我想让动捕输出的**位置不受偏航归零的影响**，这样归零操作不会引入位置漂移。
8. 作为操作者，我想让动捕链路在**飞机解锁之前就开始输出**位姿，这样 EKF2 在解锁时已经有收敛的视觉估计（PX4 要求解锁前必须有定位）。
9. 作为开发者，我想让原点的锁定发生在**解锁上升沿**并记录到日志，这样飞行后我能复核原点是否在预期时刻被锁定。
10. 作为操作者，我想在动捕数据**中断超过阈值**时看到明确的告警，这样我不会在定位已经失效的情况下继续飞。

### Offboard 与状态机

11. 作为开发者，我想让飞控状态与程序状态在代码里**显式分开**（「谁在控制飞机」与「程序在干什么」两个维度），这样状态转移的条件可以被独立推理和测试。
12. 作为操作者，我想在按遥控器开始键之前，程序**不发送任何控制指令**，这样飞机在我不期望的时候不会进入 offboard。
13. 作为操作者，我想让飞机在进入 offboard 后**先原地悬停**再执行轨迹，这样我有一个观察飞机是否稳定的窗口，可以随时中止。
14. 作为操作者，我想让三条轨迹通过**启动脚本里输入数字**来选择，这样我不需要为每条轨迹改代码或重新 launch。
15. 作为操作者，我想在轨迹执行过程中能**看到当前处于哪个状态**，这样我判断飞机行为时知道它"应该"在做什么。
16. 作为操作者，我想让程序在遥控器**任意打杆**时立刻把控制权交还遥控器，这样这是我在紧急情况下最后、也最可靠的一道防线。
17. 作为操作者，我想让 **offboard 心跳丢失**时飞控按预配置的失效保护动作执行，这样即使机载电脑节点崩溃，飞机也不会失控飞走。
18. 作为开发者，我想让 FSM 对**每条输入消息都有超时判据**（动捕、飞控状态、遥控器），这样单条链路静默失效时状态机会做出反应而不是继续发指令。
19. 作为操作者，我想在**电池电压过低**时程序主动中止任务，这样我不会把电池飞到损伤电压以下。
20. 作为操作者，我想在任务结束时飞机**自动降落并上锁**，这样我不需要手动接管降落。

### 轨迹与判据

21. 作为操作者，我想让起飞目标高度是**1 m**，这样涵道机在动捕棚里有足够的离地间隙和视野余量。
22. 作为操作者，我想让正方形轨迹边长 **1 m**、八字半径 **0.5 m**，这样轨迹完全落在动捕棚的有效捕捉范围内。
23. 作为开发者，我想让三条轨迹都在**轨迹原点**（而非动捕棚原点）下定义，这样轨迹位置与相对位姿的口径一致。
24. 作为操作者，我想让"悬停稳定"有**可量化的判据**（位置误差阈值 + 持续时间），这样"稳定后再划轨迹"不是我的主观感觉，而是程序可判定的条件。
25. 作为操作者，我想在飞机偏离目标超过安全阈值时程序能**主动中止**，这样轨迹跟踪失败不会演变成撞墙。
26. 作为开发者，我想让参考轨迹同时给出**前馈速度**（而不只是位置），这样定点出现低频抖动时我有标准的调优路径可走。

### 可验证性与诊断

27. 作为开发者，我想让整条链路的输入输出**都能被录制和回放**，这样我可以在不飞飞机的情况下复现问题。
28. 作为开发者，我想让坐标系变换的方向在**源码层面被确认**（而不是靠飞行试验反推），这样我不会在"飞机往反方向飞"时浪费一整轮实飞。
29. 作为操作者，我想在实飞前有一个**不需要飞机的静态验证流程**，这样符号错误在装桨之前就被发现。
30. 作为开发者，我想让每次飞行的关键信号（目标位置、实际位置、状态转移、电压）被记录，这样飞行后我能复盘而不只是依赖记忆。
31. 作为未来的协作者，我想让包结构、话题接口、坐标系约定都有文字记录，这样接手时不必重新推导。

### 安全与流程

32. 作为操作者，我想让首次实飞**拆掉桨叶**做地面验证，这样控制方向错误不会造成伤害。
33. 作为操作者，我想让第二次实飞**系绳并只离地 20 cm**，这样即使控制发散也不会造成损坏。
34. 作为操作者，我想随时能**一键退回纯遥控器飞行**，这样任何阶段的异常都有确定的退出路径。
35. 作为操作者，我想在首次上电时**核对电池电流读数**，这样我能确认这个已知的硬件采样缺陷是否存在。

## Implementation Decisions

### 控制层级与接口

- **控制层级选 `(A)` 级**：机载电脑下发**位置 + 偏航**，PX4 跑全部内环。选它的唯一理由是"验证 offboard 链路通不通"——对最终目标而言 (A) 级会被 PX4 自己的位置环再处理一遍，**做了等于没做**，所以它只是 Phase 1 的脚手架，不是终点。
- **中间件只用 mavros2**，完全不引入 uXRCE-DDS。Phase 2 才引入后者，且**只在控制指令方向**使用（动捕仍走 mavros2），避免两个中间件都变更。
- **状态源分流**：动捕位姿既发给 PX4（走 `/mavros/vision_pose/pose`，供 EKF2 融合，充当安全网），也发给控制节点（直接作为状态输入）。**两条链路独立，可独立失败。**

### 坐标系（★ 写死，不靠记忆）

- **动捕 / ROS 侧为 ENU**（东-北-天），**PX4 侧世界系为 NED**（北-东-地）。两者之间**是交换 x/y 并翻转 z**，**不是简单取反**。本项目文档中已记录该错误曾被写反。
- **姿态只归零偏航**，位置不受姿态处理影响。这是经过一次明确的取舍后确定的（曾有"连位置一起旋转"的提案，被否掉）。
- **原点锁定分两阶段**：节点启动时用一个"开机锁定"的原点先输出（保证解锁前 EKF2 有视觉数据），**解锁上升沿**切换为"起飞前静止帧"原点。两阶段之间的切换**不得产生位置跳变**。
- **mavros 会在它自己的边界上做 ENU↔NED 转换**，入向与出向的转换方向**不同**，已通过读 mavros 源码确认，不靠推断。
- 时间戳不前进的位姿消息**会被静默丢弃**——因此不得给动捕消息打固定时间戳。

### 包与模块

四个包，边界按"数据形态"切：

| 模块 | 职责 | 形态 |
|---|---|---|
| `vrpn_listener` | VRPN → ROS 话题 | **vendored 原样**，不得修改 |
| `mocap` | 刚体位姿 → 相对位姿（原点锁定 + 仅 yaw 归零），**输出仍是 ENU** | 纯转换为主 |
| `traj` | 参考轨迹生成（三条） | 纯函数为主 |
| `control` | FSM + offboard 指令下发 | 状态机 + mavros 客户端 |

- ★ **`mocap` 不做任何坐标转换（Q14=a）**：它只输出**动捕原生的 ENU 相对位姿**（`/mocap/pose_enu`）。ENU→NED 与 FLU→FRD **全部由 mavros 在自己的边界上完成**（三条转换已读 mavros 源码确认，见 [`phase1-implementation.md`](../../docs/control/phase1-implementation.md) §3.2）。旧版设计里"`mocap` 是我们自己做坐标转换的地方 + 另发一条 `/mocap/pose_ned`"**已废弃**。
- **`mocap` 的转换逻辑必须与 ROS 解耦**，使其可作为纯函数被测试。这是本项目**唯一的刻意测试性设计**，理由是位姿处理错误在话题层面**没有诊断分辨率**。
- `control` 的状态机设计借鉴 `Fast-Drone-XI35` 的 `PX4CtrlFSM` 的**状态划分与转移条件**（其超时/电压/RC 接管判据经过实机验证）—— 转换条件表见 [`xi35-fsm.md`](../../docs/reference/xi35-fsm.md)，但**不抄它的控制器**（那是 (B) 级姿态接口，层级不同）。
- 参数值**一律不抄** `Fast-Drone-XI35` 的配置文件——其质量参数是 0.645 kg，z0 实测 750 g，差 16%，会直接导致悬停推力系统性偏低。该文件另有一处重复定义（`rc_reverse` 出现两次），说明它被反复覆盖编辑过，不可假设内部自洽。

### 状态机（原型 snippet，来自设计讨论）

两个正交维度显式分开，而非扁平枚举：

```
控制权：   MANUAL  ──(开始信号)──▶ AUTO  ──(RC 打杆 / 超时 / 异常)──▶ MANUAL
任务态：   IDLE ─▶ TAKEOFF ─▶ HOVER ─▶ TRACK ─▶ LAND
                              ▲          │
                              └──────────┘（轨迹结束 / 中止）
```

- 状态名与转移条件**逐条对齐** `px4ctrl`，因为那些看起来多余的判断"每一条都是用事故换来的"。（对齐的是**条件与语义**，不是代码行 —— 见 Q1=a：设计移植，不抄行。）
- **必须实现的三个细节**（来自 `px4ctrl` 的实飞经验）：消息超时检查、输入边沿检测（`triggered` 语义）、以及急停信号与 PX4 模式开关**不共用通道**。

### 接口约定

- **输入**：`/vrpn/<刚体名>/pose`（geometry_msgs/PoseStamped）
- **输出**：`/mavros/setpoint_raw/local`（mavros_msgs/PositionTarget），另经 `/mavros/set_mode`、`/mavros/cmd/arming` 管理模式与解锁
- **喂给 EKF2**：`/mavros/vision_pose/pose`
- `PositionTarget.type_mask` 采用"位置 + yaw"组合（加速度与 yaw_rate 置位忽略）。**调优路径**：若定点出现低频抖动，改为同时给速度前馈（掩码只忽略加速度与 yaw_rate）。
- **`TrajectorySetpoint` 没有 `thrust` 字段**——(A) 级不受影响，但记录在案以免未来误用。

### 消息时间戳

所有发往 PX4 的消息使用**微秒**时间戳。时间戳单位错误不会报错，只会表现为"消息没人收"。

## Testing Decisions

> ★ **全项目 seam 形态（2026-09-20 确认，跨三阶段盘点）**：本项目一共只有 **2 种自动化 seam 形态**
> 加 **2 道人工关卡**，且**没有一处是重复造出来的**：
>
> | 形态 | 本项目实例 |
> |---|---|
> | **形态 A** —— 喂脚本化输入话题 + 断言发出的话题 + 假 peer | **本节的 seam 1 ＝ 形态 A 的基准定义**；phase2 的 seam 1 是它的**第二次应用** |
> | **形态 B** —— 在「话题边界上没有诊断分辨率」处开更细的 seam | **本节的 seam 2**；phase2 的 seam 2 是同一理由的第二次应用（开在求解器上） |
>
> **人工关卡**（不是 seam）：phase2 的 SITL 闭环、phase3 的实机阶梯。
> **phase3 不新增任何 seam** —— 它复用 phase2 的 seam 1。这是刻意的：seam 越少越好。

### 好的测试是什么

**只断言外部可观测行为**，不断言内部实现。在本项目里这意味着：**断言"喂进某个动捕位姿序列，发出什么 setpoint"**，而不是断言某个类的方法被调用了几次。测试不应因为重构包内部分解而失败，只应因为行为改变而失败。

### seam 1（主）：整条栈的对外 ROS 话题边界

**这是要用的最高 seam。** `mocap` / `traj` / `control` 三个包被当作一个整体，通过它对外的话题边界测试：

- **喂入端**：脚本化的 `/vrpn/<刚体>/pose` 发布者（或 rosbag 回放），以及一个**假 mavros**——它能接受 setpoint 话题并发出 `/mavros/state` 等入向消息。
- **断言端**：发布到 mavros 出向话题的 setpoint 序列。

**为什么用假 mavros 而不是 SITL**：状态机里那些"实飞才会想到的判据"（消息超时、电压跌落、RC 夺权、offboard 掉线）**都需要控制时间和注入异常**——真实 SITL 无法让 `/mavros/state` 静默 0.5 秒，假 mavros 可以。**SITL 因此降级为"上机前手动跑一次的集成关卡"，不进自动化测试。**

这个 seam 一次覆盖：原点锁定、仅 yaw 归零、三条轨迹的参考生成、FSM 的全部转移、指令字段与掩码。（**不含 ENU→NED 转换** —— 那已不在本项目代码里，见 seam 2。）

### seam 2（例外，经论证）：`mocap` 的纯转换函数

**为什么要开这个例外**：seam 1 有一个致命盲区——**当飞机往反方向飞时，它不会告诉我是原点锁错了、yaw 归零错了、还是 mavros 的边界转换不如预期**。而坐标系是本项目文档中反复标记的"耗时最多的坑"，原话是 *"在飞之前确认符号，比在飞之后 debug 便宜一百倍"*。

> 📌 **转换的归属已定（Q14=a）**：`mocap` **不做任何坐标转换**，只输出动捕原生的 ENU 相对位姿。ENU→NED 与 FLU→FRD **全由 mavros 在自己的边界上完成**。所以**本项目代码里已经不存在 ENU→NED 这一步**，下面要直接单测的是相对位姿本身。

所以对三个纯函数做直接单测：

| 函数 | 断言 |
|---|---|
| 相对位置计算（原点减法） | 输出 = 当前位姿 − 锁定原点，**逐轴独立**、不受姿态处理影响 |
| 仅归零偏航的姿态处理 | 位置输出不受影响；归零后机体 z 轴方向不变 |
| 两阶段原点锁定 | 解锁上升沿前后分别使用正确原点；**切换瞬间不产生位置跳变** |

三者都是 `(位姿, 原点) → 位姿` 的纯函数，**零 ROS 依赖**，测试成本接近零，但挡住的是"飞起来才发现"的一整类错误。

**这是刻意的 2 而非 1**。若强行压到 1 个 seam，这组断言只能并入 seam 1 做端到端验证——代价是单个失败用例的**定位成本**高一个数量级。

### 被测试的模块

`mocap`（重点）、`traj`、`control`。`vrpn_listener` **不测**——它是 vendored 且已有实机验证，测它等于替上游维护。

### 先例

本仓库目前**没有测试**（`src/` 尚未创建），所以这是**首个测试先例**，没有既有惯例可循。可参考的最近先例是 `Fast-Drone-XI35` 的 `motion_capture` 包——它对 pose/twist/accel 做插值对齐，结构上同样是"纯数据处理"模块。

## Further Notes

### ⚠️ 阻塞项：4 件必须由人物理完成的事

这四件无法由 agent 代劳，**Phase 1 开始前需要**：

| # | 做什么 | 用来确认 |
|---|---|---|
| 1 | 把 Jetson 连到**动捕所在的那个 WiFi**（不是校园 802.1x），验证能 ping 通动捕主机 | 当前实测走校园网关，**100% 丢包** |
| 2 | 在 QGC 记录**飞控实际报出的固件版本号**，并看**电池电流读数**（未解锁应 ≈0） | 版本问题的**唯一终审** + 下面那条 ADC 缺陷 |
| 3 | 确认飞控接的是 `/dev/ttyTHS1` 还是 `/dev/ttyTHS2` | 实测本机只有这两个串口 |
| 4 | 实飞时确认**遥控器开始键对应哪个通道** | 急停通道不能与 PX4 模式开关（`RC_MAP_FLTMODE`）冲突 |

> ★ **已定（Q19 / 2026-09-20）：具体通道的决定留到 ticket 层解决。**
>
> 本 spec **只固定约束、不固定通道号**：
>
> - 急停/开始信号**不得**与 PX4 模式开关（`RC_MAP_FLTMODE`）共用通道；
> - 已知 `RC_MAP_FLTMODE` 已占用一个通道，**只剩 ch7 空闲**；
> - "开始"与"急停"**是否复用同一通道**、以及解锁方式（遥控解锁 vs 程序解锁），**均未定**。
>
> **→ 后续的 ticket 化步骤必须产出一张 ticket**（建议标题：「决定遥控通道分配：开始 / 急停 / 解锁」），
> 且它必须在 Phase 1 实施到 FSM 的**「开始信号」之前** resolved —— 否则安全机制缺一条腿。
> **本 spec 里这是唯一一处刻意不在 spec 层解决的设计决定。**
>
> ⚠️ **第 2 项与第 3 项互为前提**：QGC 只能通过串口连上飞控，所以先在 QGC 里看版本这件事
> 本身依赖串口通了。

### ⚠️ 一个已知的硬件缺陷（预期会中招）+ 已定决策 Q37=a

`nxt-dual` 板的电池电流采样通道**写错了**：固件里 `ADC_BATTERY_CURRENT_CHANNEL = ADC12_CH(5)`，
而电流实际接在 **PC5 = `ADC12_INP8` = 通道 8**。**版本边界已第一手核实**：

| 版本 | 该宏 |
|---|---|
| 上游 v1.14.3 | 无 `boards/hkust`（不适用） |
| 上游 v1.15.0 / fork `5ba2e91f` / fork `main` | ❌ `ADC12_CH(5)` |
| 上游 v1.16.0 / fork `pr_fix_hkust_nxt_dual` | ✅ `ADC12_CH(8)` |

（**本文旧版此处写「z0 跑的 1.14.x 连这个板级目标都还不存在」，已作废** —— z0 固件是 v1.15 世代，且 fork 上一直有 `nxt-dual`。见 [`refs-manifest.md`](../../docs/reference/refs-manifest.md) §2.5/§2.7。）

**后果**：电流/电量保护可能是假的。**上电后必须在 QGC 核对读数。**

**★ 已定（Q37=a）——分两步，不阻塞 Phase 1：**

| | 时机 | 内容 |
|---|---|---|
| **核实** | ★ **Phase 1 首飞前（阻塞）** | QGC / `listener battery_status` 看电流是否恒 0 或怪值。成本≈0 |
| **修复** | **Phase 3 实机飞行之前**（不阻塞 Phase 1，也基本不额外花钱） | 用 fork 自带的 `pr_fix_hkust_nxt_dual` @ `8161c4cd` —— 它相对 `main` **只差一行**（`CH(5)`→`CH(8)`）。因为 Q31=a 已要求从 fork 构建 SITL，**重编所需的工具链那时已经在手**，代价接近零 |

**理由**：`ADC_CHANNELS` 是**编译期宏**，参数改不了；但**电压通道未受影响**，所以 Phase 1 可用
「电压 + 计时」兜底，不必为一处电流读数在首飞前引入"刚刷的固件"这个新变量。
详见 [`params-changes.md`](../../docs/reference/params-changes.md) A4/F1 与 [`refs-manifest.md`](../../docs/reference/refs-manifest.md) §2.7(b)。

### 关于 50 ms 动捕延迟

实测端到端延迟约 **50 ms**，抖动仅 **~2–5 ms**（早期文档中"10–100 ms 抖动"的结论**已撤销**，那是错的）。50 ms 是外部状态输入的固有延迟，PID 对此无能为力，**但 Phase 1 不需要处理它**——这是 Phase 2 的 MPC（模型预测控制）才需要显式补偿的量。

### 术语纪律

**禁止在输出中单独使用裸词 `MPC`** 指代模型预测控制或 PX4 参数。本项目里 `MPC`（模型预测控制）与 PX4 的 `MPC_*` 参数前缀（Multicopter Position Controller，级联 PID）**是两个毫不相关的东西**，裸用会在 issue 标题、测试名、commit message 里造成持续性混淆。详见 [`../../CONTEXT.md`](../../CONTEXT.md) 开头。
