# `tau-analysis` —— 从飞控 ulog 量出端到端延迟 τ

服务于 ticket [`../../.scratch/phase4/issues/03-latency-tau-from-logs.md`](../../.scratch/phase4/issues/03-latency-tau-from-logs.md)
（Phase 4 spec 的「四项前置测量」之一）。

**它量的是**：动捕 (`vehicle_visual_odometry`) 相对飞控 IMU (`sensor_combined`) 的滞后。
这个数就是 Phase 2 那条「状态外推 `x + v·τ`」里的 τ（[`phase2-implementation.md`](../../docs/control/phase2-implementation.md) **D9**）。

**结论与出处**写在 [`docs/reference/mocap-setup.md`](../../docs/reference/mocap-setup.md) **§6.3**，不在本文件里。

## 为什么需要它

Phase 1/2 文档里那句「动捕延迟实测 **50 ms**」是**旧机上**量的，出处只有一行笔记
（`weisama-log/25.06.28_PX4_log.md`：「测出动捕数据延迟 50ms」）——**没有方法、没有相关峰、没有原始数据**。
z0 换了机架、换了飞控固件、换了动捕刚体，那个数**只是个参照，不是 z0 的结论**。
本工具把这件事做成可复算的：给它一份 ulog，它给出 τ 和**全部可追溯信息**。

## 快速开始

```bash
# 0) 依赖（Jetson 上已装）：pyulog numpy scipy
python3 -m pip install --user pyulog numpy scipy

# 1) 自检 —— 不需要飞机、不需要日志、不需要飞控通电
python3 tools/tau-analysis/test_tau_core.py --self-test
python3 -m pytest tools/tau-analysis/test_tau_core.py -q      # 仓库惯例的另一种跑法

# 2) 对一份 ulog 出 τ
python3 tools/tau-analysis/tau_from_ulog.py /path/to/log.ulg --fc 2.0

# 3) 留一份机器可读的结果
python3 tools/tau-analysis/tau_from_ulog.py /path/to/log.ulg --fc 2.0 --json /tmp/tau.json
```

脚本**只读本地文件**，不碰飞控、不发任何 MAVLink。

## 三个量，必须一起看

| 口径 | 比的是什么 | 用途 |
|---|---|---|
| **A** | `sensor_combined.gyro_rad` × 动捕四元数差分出的角速度 | **主口径**。同一物理量（体轴角速度），无需换算 |
| **B** | `sensor_combined.accelerometer_m_s2` × 动捕的 `quat_body_down` | 交叉口径。**不同物理量**，准静态下 `a ≈ −9.81·d̂`（预期 **负**相关）。⚠️ 只在**近乎悬停**时成立 |
| **对照** | 飞控陀螺 × **飞控自身** `vehicle_attitude` 差分出的角速度 | ★★ **这个方法自己的零点**。同一台 IMU、同一个时钟，它**必须落在 0 附近** |

> **对照不过，A / B 的数一律不采信。** 连"本该为 0"的东西都量不出 0，说明偏差出在流程里
> （重采样 / 滤波 / 求导 / 时间基），此时 A 的数是多少都没有意义。
> 这条闸门不是摆设：**它已经抓到过一个真 bug**（见下方「踩过的坑」第 1 条）。

## 时间基：为什么用 `timestamp` 而不是 `timestamp_sample`

两条序列都取 **`timestamp`** —— 即 **PX4 收到该消息的时刻**。第一手依据
（`src/modules/mavlink/mavlink_receiver.cpp`，`vehicle_visual_odometry` 的填充处）：

```cpp
odom.timestamp_sample = _mavlink_timesync.sync_stamp(vpe.usec);
...
odom.timestamp = hrt_absolute_time();
_visual_odometry_pub.publish(odom);
```

`hrt_absolute_time()` 与 `sensor_combined` **是同一个时钟** ⟹ 量到的差值就是真延迟，
**不含跨机对时误差**。`timestamp_sample` 是动捕自报的采样时刻、经 timesync 跨域换算，
另有一层不确定度，不用。

**日志里要有这两个 topic**，靠参数 `SDLOG_PROFILE` 的 bit 7（Computer Vision and Avoidance）：

| 位 | 值 | 含义 |
|---|---|---|
| bit 0 | 1 | Default |
| bit 7 | 128 | Computer Vision and Avoidance |

`SDLOG_PROFILE = 129 = 1 + 128` ⟹ **两个都在**（z0 飞控 2026-09-22 实读值，
见 [`params-changes.md`](../../docs/reference/params-changes.md)）。

## 分析窗口：不要用启发式，读日志里的解锁状态

一次飞行日志里飞机常常有**几分钟是停在地面上的**。把静止段一起拿去做互相关，
等于用一堆零去"稀释"信号 —— 实测 z0 的 log 210 前 18 MB 里 **366 s 中有 300 s 静止**，
不加这一步时三个相关**全部**掉到 `|r| ≤ 0.03`，**连对照都过不了**。

窗口取自日志的**第一手状态**：`vehicle_control_mode.flag_armed ∧ ¬vehicle_land_detected.landed`，
取最长的一段，再丢掉开头 `--warmup` 秒（起飞瞬态）。

> ⚠️ **别用"动捕位移 > 阈值"这类启发式去猜。** 本轮调试中它一度选中 **140–162 s**，
> 而那一段陀螺 RMS 只有 **0.005 rad/s**（飞机只是被人挪动）——
> 真正在飞的是**离地窗口 307.2—328.9 s**（陀螺 RMS **0.36 rad/s**）。
> **日志里写着解锁和离地状态 —— 为什么要猜。**
> （脚本仍会跑一遍该启发式并打印出来，当交叉核对：**只在与状态窗口没有交集时报警**。
> 现在这版它选中的是 **306.4—328.4 s**、与状态窗口有交集 ——
> 但那是碰巧对上，`move_eps` 一改就会变，所以它只配当核对，不配当依据。）

窗口也可手工指定：`--window T0 T1`（秒，从日志第一条算起）。

## 读分段：`极差` 大 ≠ 方法不稳

`--segments N` 把窗口切成 N 段各估一次。**没有激励的段里相关没有峰，τ 会贴到搜索窗边缘**
（±`--max-lag`），于是极差动辄几百 ms。所以每段的 **`激励σ`** 必须一起看：

```
分段 τ(激励σ)（3 段）：[-300(0.037), +57(0.099), +49(0.426)]
                        ↑σ 最小、τ 贴着窗边 = 这段飞机没怎么动
```

**`激励σ` 是逐通道沿时间求 std**，不是整段的 RMS 也不是整段的 std —— 两个错口径都实测验过：

- 整段 **RMS**：`quat_body_down` 是单位向量 ⟹ **恒等于 1**，飞机停着还是翻跟头都是 1。
- 整段 **std**：量的是**通道之间**的差异，不是**随时间**的起伏 ⟹ `body_down` 恒 ≈ 0.47，静止与翻滚分不开。

只有"沿时间去均值"才是在量"动没动"。这三条都有自检用例钉着。

## 踩过的坑（★ 都是真发生过的，不是假设）

### 1. ★★ 两侧各按自己的 `t[0]` 建网格 ⟹ 错位直接加进 τ（**静默**）

`resample_uniform` 曾经两次调用都不传网格原点，于是各按**自己的** `t[0]` 建网格，
两条序列被错开 `t_b[0] − t_a[0]`。IMU 164 Hz、动捕 30 Hz，裁剪到共同区间后首样本
天然差最多**半个采样周期**（30 Hz 下 **16.7 ms**）。

**为什么极难发现**：整个相关峰被平移，**`r` 照样是 1.000**。表现是"同一个窗口
换个 `--segments` 就能让 τ 从 +53 ms 跳到 +20 ms"。

自检里的真值对：真 τ = 0 时，旧实现给 **−33.3 ms（r = +1.000）**，修后给 **−0.0 ms**。

### 2. ★ 把 `warmup_s` 透传给每一段 ⟹ 分段全空（**静默**）

21.9 s 的窗口切 6 段、每段 3.65 s，每段再各扣 3 s 预热 ⟹ 只剩 0.65 s，
一律以"重叠太短"被拒，分段返回空数组。看着像"这段数据不支持分段"，
其实是**起飞瞬态只发生一次，不该扣 N 次**。

### 3. ★ 零方差要**在搜峰之前**拒掉

飞机没动时 `argmax(|r|)` 只能挑噪声，τ 会**稳定地贴在下标 0 或最后一格**（= ±`max_lag`），
看着像个正经数字。实测在"飞机没动"的 SITL 日志上正是这么表现的。

### 4. ★ "锐度"和"半高全宽"都不能当"可不可信"的判据

- `|r_peak| / std(r)`：**依赖搜索窗**。同一份数据、同一条曲线，窗从 ±50 ms 放宽到
  ±300 ms 会让它从 7.7 掉到 2.3 —— 拿它判可信度等于在判窗宽。
- 半高全宽：看着与窗无关，**实测也仍然与窗有关**（194 ms @ ±150 ms 窗 vs 226 ms @ ±300 ms 窗）。
  原因是这类信号的相关峰**本身就是平顶的**，"半高落在哪一点"没有定义。

⟹ 这两个量**已从代码里删掉**，并有自检用例钉着不让加回来。
**`r_peak`（有没有咬住）+ 分段离散度（换个时间窗还对不对得上）才是可复现的量。**

### 5. 求四元数增量时记在区间**左端** ⟹ 凭空 +16.7 ms

`quat_to_rate(attrib="left")` 把 30 Hz 的半个采样周期加进 τ，足以把 50 ms 说成 67 ms。
默认 `"midpoint"`（二阶精度、无系统性滞后），**除非刻意复现某个旧口径，不要用 `"left"`**。

## 自检

```bash
python3 tools/tau-analysis/test_tau_core.py --self-test
```

判据全部是**合成信号上的真值对**：给一个已知的 τ，看能不能原样收回来。
另有若干条**钉住被否掉的方案与已修的 bug** 的用例（左端归属、锐度、半高全宽、
零方差拒答、预热扣重、网格原点、激励量口径）—— 改动它们会立刻红。

`tau_core.py` **不 import** `pyulog` / `pymavlink` / `rclpy`，也不读文件：
它只吃两条 `(t, x)` 序列。所以自检**不需要飞机、不需要日志、不需要飞控通电**。

## 依赖

`pyulog`（读 ulog）、`numpy`、`scipy`（`butter`/`filtfilt`）。三者 z0 的 Jetson 上均已装。

> `filtfilt` 的边界填充要求长度 > 3×(order+1)；样本太少时 `lowpass_zero_phase` 原样返回，
> 不报错也不滤 —— 这是刻意的（宁可不滤，也不要在边界造出假的台阶）。
