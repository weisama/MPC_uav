## 1. 四个方案

"模型预测控制输出什么给 PX4"有四个层级。层级越低，模型预测控制承担的越多，PX4 承担的越少。

| | 模型预测控制输出 | PX4 承担 | 消息 | 需要 PX4 定位吗 |
|---|---|---|---|---|
| **(A)** | 位置 / 速度 | **整个内环**（姿态 + 角速率） | `TrajectorySetpoint` | ✅ 需要 |
| **(B)** | 姿态 + 推力 | 角速率环 | `VehicleAttitudeSetpoint` | ❌ 不需要 |
| **(C)** ★ | **角速率 + 推力** | **仅角速率环** | `VehicleRatesSetpoint` | ❌ 不需要 |
| **(D)** | 电机指令 | **无**（绕过控制分配） | `ActuatorMotors` | ❌ 不需要 |

### 1.1 逐项评估

**(A) 位置/速度 —— ❌ 不可取**

模型预测控制算出的位置/速度指令**会被 PX4 自己的位置环（`MPC_XY_P`、`MPC_XY_VEL_P_ACC` 等 PID）再处理一遍**。也就是说，模型预测控制好不容易算出的最优解，最终执行的是 PX4 的 PID 输出。

→ **做了等于没做。** 唯一的例外是把它当作"验证 Offboard 链路通不通"的第一步。

**(B) 姿态 + 推力 —— ⚠️ 可行但不推荐**

- ⚠️ **模型预测控制的姿态环与 PX4 的角速率环带宽会打架**：模型预测控制以 100 Hz 假设姿态能立刻到位，而实际内环有延迟。
- ⚠️ **四元数 setpoint 的 yaw 处理麻烦**：`VehicleAttitudeSetpoint` 用四元数，但 yaw 的"绕圈"问题需要用 `VehicleRatesSetpoint` 的 yaw rate 才能自然处理。PX4 的 `TrajectorySetpoint` 里 `yaw` 和 `yawspeed` 二选一的设计正说明这是个真问题。
- ✅ 优点：中层，如果角速率环调得不好，(B) 能提供一层缓冲。

**(C) 角速率 + 推力 —— ✅ 推荐主线**

见第 2 节的四条论据。

**(D) 电机指令 —— ⚠️ 终点，不是起点**

- ✅ 理论上最彻底：模型预测控制/INDI 完全掌握执行机构
- ❌ **代价严重**：绕过 PX4 的 `control_allocator` 意味着**动力饱和保护、失控保护、混控校验全部失效**。安全网只剩 `COM_RC_OVERRIDE` 打杆接管，而它本身还依赖遥控器链路是通的（见 [`../reference/params-analysis.md`](../reference/params-analysis.md) 3.9）。
- → **应该作为 `(C) + INDI` 稳定之后的下一步，而不是第一版。**

### 1.2 ⚠️ 两个必须避免的实现错误

1. **(B) 不能用 `TrajectorySetpoint` 实现。** 该消息**根本没有 `thrust` 字段**（只有 `position`/`velocity`/`acceleration`/`jerk`/`yaw`/`yawspeed`）。**(B) 的正确消息是 `VehicleAttitudeSetpoint`。**

2. **推力是 `[-1, 1]` 归一化，不是 `0–1`。** 也不是"相对悬停"，也不是牛顿。

## 2. 为什么推荐 `(C)` —— 四条独立论据

### 论据一：模型最简

`(C)` 只需把模型建到 **"刚体动力学 + 推力/力矩"** 这一层：

- ❌ **不需要电机模型**（时间常数、转速-推力曲线）
- ❌ **不需要精确标定混控矩阵**
- ❌ **不需要知道桨的旋向**

**转向约定、桨的推力系数、混控这些坑，全部留给 PX4。** 对一个模型参数还在靠辨识的项目，这是巨大的风险削减。

### 论据二：带宽分层合理

```
模型预测控制    100 Hz  ──▶  ω_des, T_des
PX4 rate       1 kHz   ──▶  电机
```

外环（位置/姿态）带宽低于内环（角速率）一个数量级，是标准做法。`(C)` 正好切在这个分界上。

### 论据三：★ 架构解耦（最重要的论据）

PX4 官方 Offboard 文档明确标注：**attitude / body_rate / thrust_and_torque / direct_actuator 这四层，都不需要状态估计（"none"）。**

**含义**：

```
选 (C) 之后 ──▶  模型预测控制这条链完全不依赖 PX4 的位置估计
                 动捕位姿 ──直接──▶ 模型预测控制
                 模型预测控制 ──ω_des,T_des──▶ PX4 角速率环
                 PX4 有没有定位，不影响模型预测控制工作
```

→ **"动捕 → PX4 EKF2" 从"必需"降级为"安全网"。**
→ **两条链路可以独立调试、独立失败。** 出问题时能快速二分定位：是模型预测控制的问题，还是定位的问题？

> 这个性质在调试阶段的**价值极大**。它直接支撑了 [`../PROJECT.md`](../PROJECT.md) 里程碑 1 的安排：**先把动捕链路跑通，再上模型预测控制。**

### 论据四：两份独立佐证

| 佐证 | 内容 |
|---|---|
| **`agilicious`** | 它的模型预测控制 **输出就是 CTBR**（Collective Thrust + Body Rate），且它的 Bridge 层**只有 sbus/ctrl/laird/RotorS —— 不走 PX4、不走 mavros** |
| **`DISCOWER/px4-mpc`** | 用 acados 生成模型预测控制，**发布 `/fmu/in/vehicle_rates_setpoint`** —— 与 `(C)` **完全一致**，有约 210 ★，**是现成蓝本** |

两份佐证来自**完全不同的技术路线**（一个自研 Bridge，一个 PX4 Offboard），却收敛到同一个输出形式 —— 这本身就是强信号。

## 3. 演进路线：`(C)` → `(C)+INDI` → `(D)`

**核心原则：每一步都保留上一步的模型与接口，只换内环。**

```
步骤 1 ─────────────────────────────────────────────────────────
   模型预测控制 ──ω_des, T_des──uXRCE-DDS──▶ PX4 角速率环 ──DShot──▶ 电机
   ✅ 改动最小，最快能飞
   ⚠️ 内环是 PX4 的 PID，带宽与模型不匹配

步骤 2 ─────────────────────────────────────────────────────────
   模型预测控制 ──ω_des, T_des──▶ INDI ──▶ PX4 角速率环 ──DShot──▶ 电机
   ✅ INDI 前馈补偿，跟踪精度提升
   ✅ 仍保留 PX4 的安全网

步骤 3 ─────────────────────────────────────────────────────────
   模型预测控制 ──ω_des, T_des──▶ INDI ────────────────────────▶ 电机
   ✅ 完全掌握执行机构
   ⚠️ 失去 PX4 的分配器与安全网
```

### 3.1 为什么 INDI 是这个项目的自然选择

**INDI = Incremental Nonlinear Dynamic Inversion（增量式非线性动态逆）**

核心思想（不依赖精确模型）：

```
利用：ω̇ = ω̇_meas + G·(u − u₀)
求解：u = u₀ + G⁻¹·(ω̇_des − ω̇_meas)

其中 u₀ = 上一时刻的实际操纵量（已知）
     ω̇_meas = 当前测得的角加速度（IMU 可测）
     G = 操纵效能矩阵
```

**★ 关键性质：它不需要"从操纵量到角加速度"的绝对映射，只需要"增量"的映射。**
→ 模型误差、**电压 sag 导致的推力漂移**、气动变化**都被自动抵消**。

**三条支持证据**：

1. **对本项目特别合适**：模型参数全靠辨识、**还有电池 sag**（见 [`../reference/hardware.md`](../reference/hardware.md) 第 6.2 节）。INDI 对这两类不确定性天然免疫。
2. **`agilicious` 的 controllers 列表里同时有模型预测控制、几何控制、PID 和 INDI** —— INDI 在其架构里**就是内环**。
3. **用户自己仓库里的论文明确支持**：`Sun2022_TRO_NMPC_vs_DFBC.pdf` 的结论 —— *"两者加内环 INDI + 气动阻力模型后跟踪误差降低 78 % 以上"*。

> 📌 **可以把"INDI 是否值得做"变成一个有数据支撑的实验**：步骤 1 和步骤 2 用同一套模型预测控制、同一条轨迹，对比跟踪误差。**这直接就是一个论文级的结果。**

## 4. 模型预测控制的模型结构

### 4.1 状态与输入（`(C)` 方案）

```
状态 x ∈ ℝ¹³:
   p    ∈ ℝ³    位置（世界系）
   v    ∈ ℝ³    速度（世界系）
   q    ∈ ℝ⁴    姿态四元数（机体 → 世界）
   ω    ∈ ℝ³    机体角速率

输入 u ∈ ℝ⁴:
   T     ∈ ℝ    总推力（沿机体 +z 方向，即推力方向；见下方更正）
   ω_des ∈ ℝ³   机体角速率期望值  ← 直接下发给 PX4
```

> ⚠️ **【已更正 2026-09-18】本节原先写「`T` 沿机体 `-z` 方向，即 FRD 的 z 轴负方向」，与下面的公式自相矛盾。**
> 决议后的约定是 **ENU/FLU**（依据 `Sun2022` §III.A 与 `Foehn2022` §D.1，见 [`phase2-implementation.md`](phase2-implementation.md) §3.2）：
> **世界系 z 朝上、机体 z 沿推力方向**。所以 `T` 沿机体 **+z**，`g = [0,0,−9.81]`。
> 原文的 `-z`（FRD）表述若成立，下面的 `v̇` 公式必须写成 `v̇ = g − (1/m)R(q)e_z T` 且 `g = [0,0,+9.81]` —— **两行只能对一个**。

### 4.2 动力学

```
ṗ = v
v̇ = g + (1/m)·R(q)·e_z·T                ← ENU/FLU 约定；g = [0,0,-9.81]，T ≥ 0 沿机体 +z
q̇ = ½·q ⊗ [0, ω_des]                    ← 用 ω_des 代替真实 ω
ω̇ = k_ω·(ω_des − ω)                     ← 内环一阶模型
```

**最后两行的解释（重要）**：

- `q̇` 里**直接用 `ω_des` 当真实角速率** —— 这假设内环"完美跟踪"。**这是步骤 1 的简化。**
- `ω̇` 那一行是**更精细的写法**：显式建模内环为一阶惯性环节（时间常数 `1/k_ω`）。
  **这个 `k_ω` 就是步骤 1 → 步骤 2 的关键收益点**：把内环延迟显式建模进模型预测控制，模型预测控制就知道"我发的 ω_des 不会立刻生效"。

> 📌 **`k_ω` 的辨识**：给一个角速率阶跃指令，看 IMU 实际响应。**这是一个简单的台架/低空实验**，值得做。

### 4.3 约束（★ 直接决定模型预测控制能不能飞）

| 约束 | 形式 | 值 | 来源 |
|---|---|---|---|
| **推力上下限** | `T_min ≤ T ≤ T_max` | ⚠️ **`T_max` 按电池设，不按电机设！** | [`hardware.md`](../reference/hardware.md) 6.2 |
| 角速率上限 | `|ω_des,i| ≤ ω_max,i` | 横滚/俯仰 **3.84 rad/s**，偏航 **6.28 rad/s** | `MC_*RATE_MAX` |
| 倾角上限 | `R(q)·e_z · e_z ≥ cos(θ_max)` | **`θ_max = 45°`**（= z0 现值 = PX4 默认）。⚠️ **不是 30°** —— 那版 2026-09-28 被操作者裁定作废（「两边都回 45」）。⚠️ **且本约束尚未实现**：OCP 现在只有 `lbu/ubu = [F ∈ [0, T_max]] × [ω ∈ ±ω_max]` | 见 [`phase2-implementation.md`](phase2-implementation.md) **§3.3.4**（量纲依据：`hover_thrust = 1/(T/W)` ⟹ 当前推重比下物理天花板 51.3°）|
| 位置/速度（软） | 代价项而非硬约束 | 最大 **2.0 m/s**（★ 2026-09-22 更正，原写 12） | `MPC_XY_VEL_MAX` |

> ★ **2026-09-22 更正上表最后一行**：原文抄的是飞控现值 `MPC_XY_VEL_MAX = 12.0`，
> 但 **ticket 15 的人裁定已把它改成 `2.0`**（`12 m/s` 对 152 mm 涵道机是失控速度；
> Phase 1 轨迹上限 ≤0.5 m/s，`2.0` 留 4× 余量）。
> ⟹ **本文档做 Phase 2 约束设计时要抄 `2.0`**，否则模型预测控制的软约束比飞控实际允许的
> 大 6 倍 —— 且两边不一致时是**静默的**（飞控只是提前限速，不报错）。
> 逐条处置见 [`../reference/params-changes.md`](../reference/params-changes.md) **§I** 与 §E3 的注。

> ★★ **`T_max` 的取值是本文件最重要的一条工程判断。**
>
> 按电机能力算是 40 N，按电池能力算只有 **11.8 ~ 18.7 N**。**如果按 40 N 设约束，模型预测控制会算出物理上供不出来的推力指令**：
> - 电压被拉垮
> - 拉垮后同样的油门给出更小的推力（正反馈）
> - 飞机掉高度，模型预测控制加大油门，情况更糟
>
> **正确做法：`T_max` 取电池可持续供出的值，并留余量。**

### 4.4 代价函数

参考 `px4-mpc` 的做法（`NONLINEAR_LS`）：

```
J = Σₖ ‖x_k − x_ref,k‖²_Q + ‖u_k − u_ref,k‖²_R + ‖u_N − u_ref,N‖²_RN
```

- `x_ref`：参考轨迹（位置 + 速度 + 姿态 + 角速率）
- `u_ref`：**悬停推力 `T_hover = m·g = 7.36 N`** 是这里最可靠的参考值
- `Q`/`R` 的调参：**建议从位置权重高、输入权重低开始**，逐步加大输入权重压制抖动

### 4.5 求解器配置

```
N     = 50                预测步数
Tf    = 1.0 s             预测时域
cost  = NONLINEAR_LS
qp    = PARTIAL_CONDENSING_HPIPM
hess  = GAUSS_NEWTON
int   = ERK, 4 stages / 3 steps
nlp   = SQP_RTI           ← 实时迭代：每周期只做一次 SQP，延迟最低
```

> 📌 **`SQP_RTI` 的理论出处就是你仓库里的那篇** `Houska2011_Automatica_RTI.pdf`（Automatica 2011, Houska et al.）—— ACADO 的自动生成实时迭代算法把非线性模型预测控制压到微秒级。**读它就能理解为什么 acados 能在 Jetson 上跑 100 Hz。**

## 7. 实时性预算

| 环节 | 预算 |
|---|---|
| 模型预测控制求解（目标） | **≤ 10 ms**（100 Hz） |
| uXRCE-DDS 传输 | ~1 ms |
| PX4 角速率环 | 1 ms（1 kHz） |
| **动捕链路延迟** | **50 ms（实测）** ← 主要矛盾 |
| **动捕时间戳抖动** | ✅ **~2–5 ms**（可忽略） |

> ✅ **【已更正】本文件早先版本在此处写的是"±10–100 ms 抖动，是一个必须先解决的前置问题"，并要求把 `stamp` 改成 `msg_time`。该结论是错误的，照做会毁掉 EKF2。**
>
> **第一手证据**（`vrpn_listener.cpp` 第 37–40 行源码注释，原文引用见 [`../reference/mocap-setup.md`](../reference/mocap-setup.md) **6.2**）：
> - `stamp = listener->now()` 是**刻意的设计**，不是缺陷
> - 抖动实际只有 **~2–5 ms**（不是 10–100 ms）
> - **动捕主机与 Jetson 的时钟差 ~4 秒**，所以改用 `msg_time` 会引入 4 秒误差
> - 用 2–5 ms 换"与 IMU/mavros 同一时钟域"，是正确的工程取舍
>
> **后果（更正后）**：
> - 真实最坏端到端延迟 ≈ 50 + 5 ≈ **55 ms**，**不是 150 ms**
> - **模型预测控制不需要为时间戳抖动做任何事**
> - ❌ **"排在模型预测控制开发之前"这个工期安排撤销** —— 没有这条前置工作
>
> **仍然建议做的一件小事**（与抖动无关）：重写动捕节点时**转发 `vrpn_listener` 的 stamp，不要二次打戳**（`vrpn_relative_pose` 第 353 行的做法会让 EKF2 认为数据比实际更新）。**NTP 同步降级为可选** —— 只有将来想用 `msg_time` 时才必须。

**★ 关于 50 ms 动捕延迟**：

- 这是**外部状态输入的固有延迟**，模型预测控制每周期拿到的状态是 50 ms 之前的
- **PID 对此无能为力**（它只看当前误差）
- **模型预测控制可以显式补偿** —— 把延迟建模成"状态滞后 N 步"，或直接做状态外推

> 📌 **这又是一个有论文价值的对比实验**：同一套模型预测控制，补偿 50 ms 延迟 vs 不补偿，看跟踪误差差异。

**★ 实时性注意事项**：

- 用 **`SQP_RTI` + 固定迭代次数**，保证**最坏执行时间有界**（不是平均时间）
- 在 Jetson 上**实测最坏耗时**，不要相信平均耗时
- 留出余量：如果 100 Hz 下最坏耗时接近 10 ms，就降到 50 Hz
