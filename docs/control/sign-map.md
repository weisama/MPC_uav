**MPC（模型预测控制）内部用世界系 ENU + 机体系 FLU；PX4 用世界系 NED + 机体系 FRD。
两者的关系只有「x 不变、y 与 z 取反」——所以映射表是纯符号翻转，不含任何矩阵或四元数。**

## 1. 这张表错了会怎样：**不会报错**

Phase 2 是 `(C)` 级 —— MPC（模型预测控制）输出**总推力 + 机体三轴角速率**，PX4 只跑角速率环与混控。
这一级**没有外层纠正**：Phase 1 里位置发错了，PX4 的位置环会把它拉回来；这里符号发反了，
PX4 收到一条**语法完全合法**的消息，然后**照做**。

四种错法全部是**静默**的：

| 错法 | 现象 |
|---|---|
| 某个角速率符号反了 | 飞机朝**反方向**倾，越纠越偏；姿态角越大越快 |
| 推力符号反了 | `+F/T_max` ⟹ **全速砸地**（`phase2-implementation.md` §6.2） |
| 推力归一化常数错了 | 不是"没劲"，而是**推力增益按比例错掉**（改了 `mass` 不改常数就是这个） |
| 世界系或机体系选错 | 输入侧要做一次四元数变换，那是"出错概率高一个数量级"的一类操作 |

⟹ 这就是它值得单独成一张票、并且必须**推导**而不能**抄**的理由。

## 3. 推导 1：要往 +x（东）飞，绕哪个轴、朝哪边倾

**前提（必须写清楚，否则这句话没有意义）**：设机头（机体 x 轴）指向世界 +x（东），即 yaw = 0。
「往 +x 飞」指的是**世界系**的 +x。机头不朝东的一般情形见本节末尾。

### 3.1 物理层：四旋翼只有推力可用

1. 四旋翼唯一的控制力是**螺旋桨推力**，而按 FLU 的**定义**，推力沿机体 **+z**（机体系 x 朝前、
   z 沿推力方向 —— `Sun2022` §III.A / `Foehn2022` §D.1 的原文见 §7 与附录）。
2. 姿态为单位阵时，推力沿世界 +z（向上），水平分量为零 ⟹ 不产生任何水平加速度。
3. 要产生朝东的加速度，**推力矢量必须朝东偏** ⟹ 必须把机体的 z 轴向世界 +x 转。
4. 绕哪根轴转：绕机体 **x**（前后轴）转，改变的是推力的**左右**分量（y）；绕机体 **z**（推力轴）
   转，推力的方向**一阶不变**（`R_z(θ)·e_z = e_z`）；**只有绕机体 y 轴转，才产生 x 方向的分量。**

### 3.2 代数层

绕机体 +y 轴转角度 `θ`（右手定则，FLU 下 +y 指向**左**）：

```
R_y(θ) = ⎡ cosθ  0  sinθ ⎤
         ⎢   0   1    0  ⎥
         ⎣−sinθ  0  cosθ ⎦
```

- 机体 z 轴在世界系里的方向：`R_y(θ)·e_z = ( sinθ, 0, cosθ )`
  ⟹ **θ > 0 时该方向有 +x 分量** ⟹ 推力朝东偏 ⟹ 向东加速。✅
- 机体 x 轴（机头）的方向：`R_y(θ)·e_x = ( cosθ, 0, −sinθ )`
  ⟹ **机头朝下（−z）**，即"下俯"。

**结论：绕机体 +y 轴正向转 ⟹ 机头下俯 ⟹ `ω_y > 0` ⟹ 向东飞。**
（这就是 FLU 下的"低头前飞"，与直觉一致：低头才能往前飞。）

### 3.3 与 PX4 自己那套（FRD/NED）交叉核对

PX4 的位置控制器里有一行**同样物理**的代码，`src/modules/mc_pos_control/PositionControl/PositionControl.cpp`
的 `_accelerationControl()`（真身 `4a0e65f2`，第一手）：

```cpp
Vector3f body_z = Vector3f(-_acc_sp(0), -_acc_sp(1), CONSTANTS_ONE_G).normalized();
```

`_acc_sp` 是 **NED** 系里的期望加速度。要往东加速时，NED 下 `_acc_sp = (0, a, 0)`，于是
`body_z = (0, −a, g)`：**机体 z 轴（FRD，即"腹部"方向）朝西偏**，也就是**机背朝东倒** ⟹ 机头下俯
（此时机头朝东，"机背朝东倒"就是低头）。✅ 与 §3.2 同一个物理结论。

> ⚠️ **这一步最容易自己骗自己**：`body_z` 的旋转发生在**世界系的北轴**上，而机体 x 轴朝东 ——
> 如果你把它当成"绕机体 x 轴转"，会得到 `roll` 而不是 `pitch`，方向完全错。
> 换算到机体系才看得出来：世界北轴 = 机体 **−y**（FRD 的 y 朝右、此时朝南）⟹ `ω_y(FRD) < 0`
> ⟹ 与 §5.2 的「pitch 取反」自洽（FLU 的 `+ω_y` 正是 FRD 的 `−ω_y`）。

### 3.4 机头不朝东时（一般形式）

把上面的话说得与航向无关。设 `d̂` 为**期望加速度在机体系（FLU）里的方向**（水平分量，单位矢量），
`ẑ` 为机体 +z（推力轴），则：

```
ω = κ · ( ẑ × d̂ )，    κ > 0          ← 要往机体系 d̂ 方向加速，就绕这根轴正向转
```

核对三个方向（`ẑ × ẑ = 0` ⟹ 纯水平方向才适用）：

| 期望加速方向 `d̂`（机体系） | `ẑ × d̂` | 需要的角速率 |
|---|---|---|
| `+x`（前） | `+y` | **`ω_y > 0`**（低头前飞，§3.2） |
| `+y`（左） | `−x` | **`ω_x < 0`**（左滚） |
| `−y`（右） | `+x` | **`ω_x > 0`**（右滚） |

⚠️ **左右两条方向不要凭"滚转就是往左/往右"想当然** —— 它的符号与 `d̂` **相反**那一侧才是对的：
机头朝东时，+y 是**北（左手边）**，要往北飞得**左滚**（`ω_x < 0`）。
这条在自检里被钉成一个一般性的用例（`test_general_rule_omega_is_z_cross_d`）。

所以 §2 那条"绕 +y 正向"是**机头朝 +x 时**的读法；一般情形用上面这条式子。

## 5. 推导 2：FLU → FRD 的角速率与推力

### 5.1 两套机体系的关系：**绕 x 轴转 180°**，不是一个"镜像"

按定义，同一台飞机上的两套标注只差两根轴的方向（`CONTEXT.md` §一）：

| | 机体 x | 机体 y | 机体 z |
|---|---|---|---|
| FLU（本项目 / 论文） | 前 | **左** | **上**（沿推力） |
| FRD（PX4） | 前 | **右** | **下** |

所以两套基的关系是 `e_x` 相同、`e_y` 与 `e_z` 各自取反。**注意行列式**：
`det diag(1, −1, −1) = +1` ⟹ 这是**绕机体 x 轴转 180° 的一个真旋转**，**不是镜像**。

★ **这一句必须显式写出来**：如果误以为它是镜像（`det = −1`），就会怀疑"角速度是轴矢量、
是不是还要再补一个负号"，而那个多余的负号会把**三根轴全翻一遍**，变成另一个静默的摔机错法。

### 5.2 角速率：同一个物理矢量在两套基里的分量

设 `ω` 是"机体相对惯性系的角速度"这个**物理矢量**。任一矢量在正交基里的分量 = 它在该基各轴上的投影。
因为 `e_x` 相同、`e_y` 与 `e_z` 取反，逐轴投影即得：

```
ω_FRD,x =  e_x·ω = +ω_FLU,x
ω_FRD,y = (−e_y)·ω = −ω_FLU,y
ω_FRD,z = (−e_z)·ω = −ω_FLU,z
```

**⟹ roll 不变号；pitch 取反；yaw 取反。** 三条都没有"额外负号"（理由见 §5.1）。

**物理旁证（两条，都不用公式）**：

- **pitch**：`+y_FLU` 是**左**轴，绕它正向转 = 机头**下俯**；`+y_FRD` 是**右**轴，绕它正向转 = 机头**上仰**。
  **同一个动作在两套标注下必然符号相反** —— 所以这一项只能是"取反"，不可能是"不变"。
- **yaw**：`+ω_z_FLU`（z 朝上）是**逆时针**（从天上看 = 左转）；`+ω_z_FRD`（z 朝下）是**顺时针 = 右转**。
  同样必然取反。

### 5.3 推力：量纲就在这一行

推力矢量**按定义**沿机体 `+z_FLU`、大小 `F ≥ 0`。同一个物理矢量在 FRD 的 z 轴（朝下）上的分量：

```
F_z_FRD = (−e_z)·(F·e_z) = −F
```

PX4 要的不是牛顿，是**归一化推力** `thrust_body ∈ [−1, 1]`（`MulticopterRateControl.cpp` 原样透传给混控器，
不做任何悬停油门重标定，见 §6）：

```
thrust_body[2] = F_z_FRD / T_max = −F / T_max        ∈ [−1, 0]（向上推力恒为负）
```

- 负号是**物理的**：FRD 下 z 朝下，向上的推力就是**负 z**。
- 上界 `0` 而不是正的：`F ≥ 0` 且 `T_max > 0`。
- 第一手旁证（`px4_msgs` `msg/VehicleRatesSetpoint.msg`，`release/1.14` @ `ffb6e80e`）：
  *"For multicopters thrust_body[0] and thrust[1] are usually 0 and **thrust_body[2] is the negative throttle demand**."*
- 第二条旁证：PX4 自己算悬停推力时给的就是负值 —— `_accelerationControl()` 里
  `collective_thrust = _acc_sp(2) · (hover_thrust / g) − hover_thrust`，悬停（`_acc_sp(2)=0`）时
  `collective_thrust = −hover_thrust`。✅

> ⚠️ **术语陷阱（`px4_msgs` 的注释会骗人）**：`VehicleRatesSetpoint.msg` 把 `roll/pitch/yaw`
> 和 `thrust_body` 都注释成 *"in (body) NED frame"*。**这里的"NED"是 PX4 对它那套机体轴的习惯叫法，
> 指的是 FRD 机体系，不是世界系 NED。** 角速度本来就是机体系量（见 §7 与附录），
> 若按字面当成世界系 NED 去理解，会多做一次世界系变换 —— 又一种静默错法。
> 我们项目里对外一律写 FRD，不用"NED 机体系"这个叫法。

## 6. 推力那一项的量纲与 `T_max`

| 项 | 值 / 来源 |
|---|---|
| 符号与量纲 | `thrust_body[2] = −F / T_max`，`F` 单位 N，`T_max` 单位 N，结果是 `[−1, 0]` 的无量纲数 |
| `T_max` 按什么取 | ★ **按电池的实际供电能力**，**不是按电机上限**（理由与实测：`phase2-implementation.md` §3.3） |
| `T_max` 的数 | z0 当前取**电池限制的保守端 ≈ 11.8 N**；**最终值由 [ticket 10](../../.scratch/phase2/issues/10-param-measure-backfill.md) 定稿并回填** |
| 换算常数怎么来 | **从模型导出**（`1/T_max`，`T_max = m·g / hover_thrust`），**禁止硬编码**（参考实现里的 `0.07` 是反面教材） |
| 为什么不能硬编码 | 模型里的 `mass` / `hover_thrust` 一改，常数不改 ⟹ 推力增益**按比例静默错掉** |

**自洽性要求（两条必须同时成立）**：

1. 模型里的 `hover_thrust` 与这里的 `T_max` **互相自洽** —— PX4 对 `thrust_body` 不做任何重标定
   （`MulticopterRateControl.cpp` 原样透传，第一手），所以悬停配平点上算出来的
   `thrust_body[2]` 必须正好是 `−T_hover / T_max`。
2. 拿 §2 的表算出的悬停指令，与 PX4 自己悬停时给的 `−hover_thrust` **同号同量级**（旁证见 §5.3）。

## 7. 为什么选 ENU/FLU，而不是 NED/FRD

**两种方案的「转换总数」相同（都恰好 1 处），差别在误差风险放在哪一侧。**

| 方案 | 转换发生在 | 需要什么 | 出错概率 |
|---|---|---|---|
| **ENU/FLU**（本方案） | **输出侧**：4 个字段的符号与归一化（精确取值见 **§2**，此处不复写） | **4 行里 3 行是纯符号翻转、1 行是「取反 + 除以 `T_max`」**，肉眼可验 | 低。且**这一侧错了闭环能立刻看出来**（飞机朝反方向倾） |
| NED/FRD | **输入侧**：动捕 ENU 四元数 → NED 四元数（+ 姿态 FLU→FRD） | 矩阵 / 四元数推导 | 高一个数量级。参考实现里那段手写 `1/√2·[w+z, x+y, x−y, w−z]` 就是这一类 |

**决策：把误差风险挪到「纯符号翻转」那一侧，而不是「四元数变换」那一侧。**

另外三条理由（同一处的记录，理由与结论放在一起 ⟹ 后人不会无意间推翻它）：

1. **输入侧零转换**：动捕原生就是 ENU（`/mocap/pose_enu`，G11），MPC（模型预测控制）内部也是 ENU
   ⟹ 状态源直接进，不经过任何坐标系变换。
2. **模型代码可以逐字复用**：参考实现 `multirotor_rate_model.py` 的 `g = [0,0,−9.81]`、
   `force = [0,0,F]` 在 ENU/FLU 下**一个字都不用改**。
3. **与依据的论文一致**：`Sun2022` §III.A 与 `Foehn2022` §D.1 的坐标系就是 ENU/FLU（原文引用见
   `phase2-implementation.md` §3.2）⟹ 论文、参考实现、动捕三者同一约定。

**代价（已知情）**：`mpc-roadmap.md` 里**倾向 NED/FRD 的表述要同步改写**。
已核对并处理的：该文件 §4.1/§4.2 的动力学公式（**已更正**，见该文件 §4.2 的更正注记）。

## 8. 代码侧契约

## 9. 可执行复核

推导是可以**跑一遍**验证的，不是只有一段散文：

```bash
python3 tools/sign-map/test_sign_map_core.py --self-test      # 或 python3 -m pytest tools/sign-map/test_sign_map_core.py -q
```

它做四件事（细节与自检清单见 [`tools/sign-map/README.md`](../../tools/sign-map/README.md)）：

1. **独立推导**：只用"两套基的轴方向"这个定义（不使用 §2 表里的任何一个符号）算出 `[+1, −1, −1]`
   与推力那一项，**再**去和权威文档里的 `sign-map:canonical` 块比。
2. **物理闭环**：把同一条指令走两条互不相干的约定 ——
   ① ENU/FLU 直接积分；② 按 §2 映射成 PX4 的 FRD/NED 量再积分 —— 断言两者给**同一个世界系加速度**。
   这一条能抓到"符号翻转表自洽但物理方向相反"的错误。
3. **反例钉死**：故意不翻 `pitch`、故意把推力写成 `+F/T_max`，断言世界系加速度确实**朝反方向 / 朝下**
   （即：这些错法真的会摔机，不是因为"看起来不对"）。
4. **三方对照**：与 `~/refs/px4-mpc` 的实际源码行、以及 `px4_msgs` 的消息定义逐条比对。
   外部仓库不在时**明确报 SKIP**，不静默通过。

## 10. 本文件**证明不了**什么（诚实交代）

- ✅ 本文件证明的是：**这套约定是自洽的、且与参考实现、`px4_msgs` 注释、PX4 自身位置控制器的物理一致。**
- ❌ **它证明不了「这套约定与真 PX4 一致」。** 符号翻转表、离线自检、假 PX4 夹具，
  三者都只在**我们自己这一侧**闭环。**唯一能回答这个问题的是 SITL 闭环**（[ticket 05](../../.scratch/phase2/issues/05-sitl-offboard-smoke.md)
  的开环单项、[ticket 09](../../.scratch/phase2/issues/09-sitl-tier-a-closed-loop.md) 的闭环判据），
  之后再交给 Phase 4 的实机阶梯。
- ⚠️ **不要为此去造一个"与被控对象同构"的 Python 闭环来自动化这件事** ——
  它与控制器**共享同一套约定**，整条约定错了它会**一起错并且通过**。
  这个方案已被考虑并否决，理由记在 [`spec.md`](../../.scratch/phase2/spec.md) 的 Testing Decisions（seam 3 一节）。
- ⚠️ 本文件给的是**方向与符号**；**数值精度**（`T_max`、`hover_thrust`、角速率上限）不在本文件，
  它们在 `phase2-implementation.md` §5 的待实测清单里，由 ticket 10 定稿。
